# Immutable QC v1: seal every file, audit in one click

Status: build spec (2026-10-13). Not published (the deploy allowlist takes no `.md`). This is the contract for the code in
`core/`, `agent/`, `app/` and the new landing page. When code and this file disagree, fix one of them in the same change.

## 1. What v1 does

1. **Seal (the agent).** A small program runs on the instrument PC, or anywhere that can read the folder where the
   instrument software saves its results. It seals every file in that folder, then keeps sealing each new or changed file
   as soon as it is written. It reads only bytes: any instrument software, any vendor, any file format, with no
   reverse engineering and no vendor cooperation. The seals go into a ledger file inside the folder.
2. **One-click audit (the app, and the agent).** Anyone with the folder drops it on `immutableqc.com/app/`. The browser
   re-reads every file, recomputes every fingerprint, checks every signature and link in the ledger, and shows one
   verdict: every file matches its seal, or exactly what does not. Nothing is uploaded. The same audit runs on the
   command line (`iqc audit`) with an exit code for pipelines. Both write a self-contained audit report.
3. **Try it in the browser.** The app can seal a folder too (key kept in the browser) and has a demo that builds a small
   sample instrument folder in memory, seals it, lets you change a file, and audits it again, so a visitor sees a pass and
   a fail within a minute without installing anything.

Out of v1 (each is "Upcoming" in any copy): anchoring heads on a public network, Merkle batches, an encrypted archive,
per-person signatures, extracting values from inside files (per-result records), lineage, sealing inside the vendor's
software before it writes the file, a Windows installer or service, an npm package, post-quantum signatures.

What a seal does and does not show (say this plainly wherever it matters): a pass shows each file is byte-for-byte the
one the agent sealed, and that the ledger has not been edited, reordered or cut since it was signed. It does not show the
file was right when it was written (a wrong value written by the instrument software is sealed as written), and it does
not cover a change made between the moment the software writes the file and the moment the agent reads it (the agent
waits for a file to stop changing for a few seconds; that window is the one gap). Someone holding the ledger's private key
could rewrite the ledger from the start; a head pinned somewhere else earlier (section 4.6) exposes that.

## 3. Ledger format, version 1

### 3.1 File
UTF-8 JSON Lines: one JSON object per line, each line ending in `\n`. Default location: `<data folder>/ImmutableQC/ledger.jsonl`
(a visible folder, so people can find it and drop it; it also holds `README.txt` and the agent's lock file `agent.lock`).
The agent never seals anything inside the `ImmutableQC` folder at the root of the data folder. A ledger may live elsewhere
(`--ledger`), for example on another drive.

Line 1 is the header; every other line is a record. Unknown top-level keys are an error. A line that is not valid JSON, a
blank line, or a last line without `\n` makes the ledger fail with the line number. Every line must be byte-for-byte the
canonical serialization of its object (`JSON.stringify` with the key order shown below, no spaces; `f` keys in payload
order): this rules out duplicate keys, padding and any second reading of a line.

### 3.2 Text rules
- Every sealed field is a JSON string. A sealed field never contains `|`, or a control character U+0000 to U+001F or U+007F.
- Times: `YYYY-MM-DDTHH:mm:ss.sssZ` (what `Date.prototype.toISOString()` gives), UTC, and a real date.
- Hex: lowercase. Fingerprints and links 64 hex, signatures 128 hex, public key 130 hex, key id 16 hex, ledger id 32 hex.
- File paths are relative to the data folder: `/` between segments, Unicode NFC, no empty, `.` or `..` segment, no leading
  `/`. The characters `%`, `|` and control characters are percent-encoded as `%25`, `%7C`, `%0A` and so on (uppercase hex);
  nothing else is encoded. `encodePath`/`decodePath` in core do this; the stored path is the encoded form.

### 3.3 Header (line 1)
```json
{"format":"immutableqc-ledger","version":1,"ledgerId":"<32 hex, random>","createdAt":"<time>","station":"<name>",
 "alg":"ECDSA-P256-SHA256","publicKey":"<130 hex: 04 || X || Y>","keyId":"<16 hex>","g":"<64 hex>","sig":"<128 hex>",
 "ctx":{"agent":"immutableqc-cli/0.1.0"}}
```
- `station`: 1 to 64 characters, the sealed-field rule applies. Default: the computer's hostname (CLI) or "Browser" (app).
- `keyId` = first 16 hex of SHA-256(the 65 public-key bytes).
- `g` (genesis) = SHA-256 of the UTF-8 text `immutableqc-ledger-v1|<ledgerId>|<createdAt>|<station>|<alg>|<publicKey>`.
- `sig` = the signature (3.6) over the 32 bytes of `g`.
- `ctx` is optional and is **not sealed**: reports show it labelled "not sealed".

### 3.4 Records (line 2 onward)
```json
{"n":1,"kind":"file","f":{...sealed fields...},"r":"<64 hex>","prev":"<64 hex>","h":"<64 hex>","sig":"<128 hex>","ctx":{...}}
```
`n` counts from 1 with no gaps. `f` holds exactly the fields of its kind. `ctx` is optional and not sealed.

| kind | sealed fields, in payload order | payload (UTF-8) | events |
|---|---|---|---|
| `file` | `station, path, sha256, bytes, observedAt, event` | `iqc-file-v1\|station\|path\|sha256\|bytes\|observedAt\|event` | `existing`, `added`, `changed`, `added-unwatched`, `changed-unwatched` |
| `file-removed` | `station, path, observedAt, event` | `iqc-file-removed-v1\|station\|path\|observedAt\|event` | `removed`, `removed-unwatched` |
| `session` | `station, event, at, agent` | `iqc-session-v1\|station\|event\|at\|agent` | `watch-started`, `watch-stopped`, `scan` |
| `reading` | `instrumentId, sensorType, value, unit, capturedAt` | `instrumentId\|sensorType\|value\|unit\|capturedAt` | none. The construction used by the docs pages and the old alpha app; verified, never produced by v1. |

- `sha256`: of the file's bytes. `bytes`: decimal size, `0` or no leading zeros. `observedAt`: when the agent finished
  reading the file. `agent`: for example `immutableqc-cli/0.1.0` or `immutableqc-app/0.1.0`.
- Events: `existing` = found on the first scan this ledger ever made (its history before that is unknown);
  `added`/`changed`/`removed` = seen while a watch session was running; the `-unwatched` forms = found by a later scan
  or watch start (it happened while nothing was watching, so its time is unknown). `ctx.modifiedAt` (the file's own
  modification time) may be recorded, unsealed.
- `reading` fields keep the docs pages' rules (numbers as text, `capturedAt` as there, which may lack milliseconds).
- Field order and tags make payloads of different kinds unable to collide (different first field or field count, and no
  field can hold `|`).

### 3.5 Fingerprint and link
- `r_n = SHA-256(payload_n)` as hex.
- `h_n = SHA-256` of the text `h_(n-1) hex + r_n hex + n in decimal` (the docs pages' link rule). `h_0 = g`.
- `prev` must equal `h_(n-1)`.

### 3.6 Signatures
ECDSA P-256 with SHA-256 (WebCrypto `{name:'ECDSA', hash:'SHA-256'}`) over the 32 bytes of the record's **link `h_n`**
(header: over `g`), IEEE P1363 `r || s` as 128 hex, **low-S only** (a signer normalizes `s` to `n - s` when `s > n/2`; a
verifier rejects high-S). Signing the link, not the fingerprint, means removing, reordering or inserting a record breaks a
signature without needing an anchor (the docs pages' demo signs `r_n`; this is the v1 improvement).

### 3.7 Verification (`verifyLedger`)
Check the header (shape, every rule above, `keyId`, `g`, signature), then every record in order: shape, field rules, event
allowed for its kind, `n`, `r`, `prev`, `h`, `sig`. Report **every** problem with its line number and a plain sentence
(not only the first), but treat the ledger as broken from the first failing record on: per-file state is built only from
the records before it. Output: header, records, problems, the head `{n, h}` of the last good record, per-path state
(latest version, every version with its record number, time and event), and watch sessions (start, stop, whether each
ended cleanly, gaps between them).

### 3.8 Audit (`audit`)
Input: a verified ledger, optionally a map of the files present (`path → {bytes, sha256}`), and optional expectations.

Per sealed path, from its latest record:
- **match**: present and its SHA-256 equals the latest sealed version.
- **changed**: present, different bytes (say if it equals an earlier sealed version: "matches the version sealed in record n").
- **missing**: latest record is a `file` record and the file is not there.
- **removed**: latest record is `file-removed` and the file is not there (fine, recorded).
- **back after removal**: latest record is `file-removed` but the file is there (a note: not sealed since).

Files present that the ledger never sealed: **not sealed** (a note). Without a file map, file states are "not checked" and
the audit covers the ledger only.

Expectations: `expectHead {n, h}` must match record `n`'s link (a ledger that has grown since still passes);
`expectKeyId` must equal the header's.

Verdict: **fail** if the ledger has any problem, a file is changed or missing, or an expectation does not match;
otherwise **pass**. Notes (never failures unless `strict`): files sealed more than once (changed after their first seal),
any `-unwatched` event, files not sealed, files back after removal, a watch session that did not end cleanly (no
`watch-stopped` before the next start), gaps between sessions. `strict` turns notes into failures.

### 3.9 Report
`renderReportHTML(report)` returns one self-contained HTML document: inline CSS, no script, no external request, prints
well on A4 and Letter. It says, in this order: the verdict in one sentence; counts; problems; notes; ledger (ledger id,
station, key id, records, head `n` and `h`, created); watch sessions; every file with its state, size, SHA-256 and
version count; method (what was recomputed, format version, the tool and its version, when, and "in a browser" or "on
the command line"); how to re-run the audit. `JSON.stringify(report)` is the machine-readable form; it carries
`format: "immutableqc-audit"`, `version: 1`.

## 4. The agent (`iqc`)

Node 20+, no dependencies. Run as `node download/iqc.mjs <command>` (the one-file download) or `node agent/bin/iqc.mjs`.

```
iqc watch [folder]   Seal everything now, then keep sealing new, changed and removed files until Ctrl+C.
iqc seal  [folder]   Seal once and exit (for a scheduler or a pipeline).
iqc audit [folder]   Check the ledger and every file. Exit 0 pass, 1 fail, 2 usage or read error.
            --report <file.html>  --json <file.json>  --expect-head <n>:<h>  --expect-key <keyId>  --strict
iqc head  [folder]   Print the current head, to pin somewhere else (an email, an ELN entry, a printout).
iqc status [folder]  Ledger, key, records, last session, and what changed since the last seal.
iqc help | --version
Common: --ledger <path>  --key <path>  --station <name>  --interval <s> (2)  --settle <s> (3)
        --ignore <glob> (repeatable; * and ?)  --quiet  --no-color (NO_COLOR is honored too)
```
- `folder` defaults to the current directory.
- **Keys.** First use creates an ECDSA P-256 key and saves the private key as JWK at
  `~/.immutableqc/keys/<keyId>.jwk` (mode 0600 where the OS has modes; folder 0700). The header carries the public key.
  Later runs load the key named by the header's `keyId` (or `--key`); if it is not on this machine, stop and say so.
- **Before appending** the agent verifies the whole existing ledger. If anything fails it refuses to write and says to
  run `iqc audit`: it never extends a broken ledger and never repairs one silently.
- **Lock.** `ImmutableQC/agent.lock` holds the pid and start time; a second agent on the same ledger refuses; a stale lock
  (pid gone) is taken over with a warning.
- **Scanning.** Poll every `--interval` seconds (works on network shares where file events do not). Walk the folder with
  `lstat`: skip symlinks, the root `ImmutableQC` folder, `--ignore` matches and the default ignores (`.DS_Store`,
  `Thumbs.db`, `desktop.ini`, `~$*`, `*.tmp`). A new or changed file (size or modification time differs from what was
  last sealed or last seen) is sealed once its size and modification time have not changed for `--settle` seconds and it
  can be opened for reading (busy or locked files are retried on the next poll; after a minute, warn once). Hash with
  streaming `createHash`; seal only if the SHA-256 differs from the latest sealed version (a touched file with the same
  bytes is not re-sealed).
- **Events.** First scan of a new ledger: `existing`. During a watch: `added`, `changed`, `removed`. At the start of a
  later watch or a `seal`: `added-unwatched`, `changed-unwatched`, `removed-unwatched`. A watch writes `watch-started`
  first and `watch-stopped` on Ctrl+C or SIGTERM; `seal` writes `scan` first.
- **Writes.** Each record is one `write` of one complete line to a file opened for append, then `fsync`.
- **Output.** Short, human lines (`sealed  QC/run-0914/injection-06.csv  1.2 MB  eb1690bc…`), colored on a terminal;
  a summary line on exit.
- Works on Windows, macOS and Linux (paths are converted to `/`; tests cover a Windows-style relative path).

## 5. The web app (`app/`)

One page, two modes, and a demo. Everything runs in the browser; the page's Content-Security-Policy forbids network
connections (`connect-src 'none'`), so "nothing is uploaded" is enforced, not promised.

- **Audit (default, the one click).** A large drop target: "Drop a data folder to audit it". Dropping the folder is the
  click: the app finds `ImmutableQC/ledger.jsonl` inside it and starts at once. Also "Choose a folder" (a directory
  picker), and if no ledger is found, it asks for the ledger file. Optional, folded away: "Pinned head" and "Expected key
  id". Progress shows files and bytes checked. Hashing runs in a Web Worker (`hash-worker.mjs`); files up to 256 MiB use
  `crypto.subtle.digest`, larger ones core's incremental SHA-256 in 8 MiB slices, so a multi-gigabyte raw file never has
  to fit in memory.
- **Verdict.** One unmistakable result: a pass ("All 1,284 files match their seals. Ledger intact.") or a fail ("2 files
  changed since they were sealed"), with icon, color and words (never color alone). Then problems, notes, the watch
  timeline, a searchable file list, the ledger details (key id, head, copy buttons), and "Download report (HTML)" and
  "(JSON)".
- **Seal (in the browser).** Drop a folder; the browser creates a key (kept in IndexedDB, not extractable), seals every
  file, and downloads `ledger.jsonl` with instructions to put it in an `ImmutableQC` folder inside the data folder. If the
  browser already holds the key of a ledger you drop, it can add a `scan` and the changes to it. The agent is the real
  tool for an instrument PC; the page says so.
- **Demo.** "Try it with sample data": builds a small instrument folder in memory (a few result files of a fictional,
  vendor-neutral instrument, CSV and a binary file), seals it, audits it (pass), offers "Change one value" (edits a file
  in memory) and audits again (fail, pointing at the file). No real data needed.
- Works by keyboard and screen reader (labelled controls, `aria-live` status, focus moved to the verdict), at 320 px wide
  and up, with `prefers-reduced-motion` respected, and with JavaScript errors shown as a readable message.

## 6. The landing page (`index.html`)

Goal: a visitor understands in five seconds what this is and in one minute has seen it work. Short (about 400 to 600
words of copy), intuitive, futuristic, fast.

Must have, in order: a headline that says the outcome in plain words; one sentence under it (seal every file as your
instruments write it; anyone can audit it in one click; your data never leaves your lab); two calls to action ("Run the
1-click demo" → `app/#demo`, "Get the agent" → the install section); a visual that shows a file being sealed and a
change being caught; three steps (install the agent on the instrument PC, every file is sealed as it is written, drop the
folder to audit in one click); why it matters (most bad data is not malicious: scripts, sync conflicts, restored backups;
results now feed models that choose the next experiment; nothing readable leaves the lab, only fingerprints); who it is
for (automated research labs first; regulated QC labs later); what works today and what is Upcoming (short); install
(download `download/iqc.mjs`, its SHA-256 printed beside the link, needs Node.js 20 or later, one command); a footer with
Docs (the document set), contact via joseqc.com, the status line and the independence line.
