How a record is sealed

1Scope

How one result becomes a sealed record, using record 6 of the synthetic sequence SEQ-0914-02. Every value was computed and checked at build; Check a record recomputes them in your browser.

2The record payload

Five fields, joined by a vertical bar with no spaces: instrument, measurement type, value, unit and capture time (UTC, ISO 8601). For record 6:

instrumentId
HPLC-02
instrument
sensorType
hplc
measurement type
value
1508811
peak area
unit
counts
unit
capturedAt
2026-09-14T08:47:50Z
capture time

The payload, 48 bytes of UTF-8:

HPLC-02|hplc|1508811|counts|2026-09-14T08:47:50Z

A field holding the bar or a control character fails the check, so two records cannot share a payload.

BasisThe alpha app’s HPLC import seals this payload for each peak area.

2.1What is not sealed yet

Injection, sample id and retention time are shown, not sealed; the alpha app does not keep sample or method yet. Sealing them is upcoming.

3The fingerprint

r6 is the SHA-256 of the payload, in lowercase hex:

eb1690bc5922a312d90ee139fdf8e20b92bf2cb0feae8ee0e70bd24fbd2b54d7

One changed character changes it completely. Recompute it in a UTF-8 terminal:

printf '%s' 'HPLC-02|hplc|1508811|counts|2026-09-14T08:47:50Z' | sha256sum

On macOS, use shasum -a 256. A fingerprint is not encryption: a plain SHA-256 of a few guessable fields can in principle be matched by trying likely values, so the records stay with the lab.

BasisSHA-256, FIPS 180-4, over the UTF-8 bytes as they are, with no Unicode normalization.

4.1How a checker reads the links

A checker recomputes each link and compares it with the stored one. A changed value fails its record’s fingerprint and signature and breaks only the link into the next record; replayed from 64 zeros, the head no longer matches the anchor (section 7).

A record removed with every later link rewritten passes, and needs no key; only an anchor taken beforehand shows it. Signatures that cover each record’s position are an upcoming feature.

5The signature (demo)

Records 1 to 8 were signed with ECDSA P-256 at build by a demo key, then discarded; its public key is on the pages that check it. That shows the method, not independent evidence: in use, the public key would be published outside the lab’s system. Demo signatures. In the alpha, one server key signs imported rows; per-analyst signatures are upcoming.

A missing signature fails. Here an edited record fails its signature after a rewrite only because the demo key is gone; whoever holds the alpha’s server key could re-sign, and only an earlier anchor would disagree.

A signature made with a system key on a record’s bytes is neither an electronic signature nor a digital signature as 21 CFR Part 11 uses those terms: both identify a person.

BasisECDSA, FIPS 186-5. IEEE P1363 encoding, in its low-S form only. Demo key id 7A15F562…

6Corrections appended with a reason

A record is never edited in place. A correction is a new record with the corrected value, a reason and the number of the record it corrects; the original stays as sealed and keeps passing, and the new head is not yet anchored. The reason and time sit beside the seal, not inside it. Here a one-time browser key signs the correction, which shows it has not changed since, not who may correct. The alpha app has no corrections yet.

7The anchor (simulated)

An anchor is a copy of a batch fingerprint kept outside the lab’s system, so that a later rewrite would show. Here it is the link of record 8, stored on the page as the anchored fingerprint (simulated, no network call).

0a35688a4c3ec82a5e621cede1f173a6d436ade0e20f159dca92c2a3711e3dc1

In use, a lab would pin that fingerprint by its own means: a pin file on another drive or share, a printout or a notebook entry. Nothing on this site or in the app writes to a network, and no ledger or outside service would be involved. The anchor would hold no value, only a 64-character code.

8What a pass and a fail show

A pass shows
The sealed fields are unchanged, the key holder signed them and the links agree; only an anchor fixes its place in the history.
A pass does not show
That the result was right at capture, who made it, or anything outside the seal. That no record was removed. That the value was ever measured: a pass shows that a record has not changed since it was sealed, not that an instrument produced it, so a value invented and then sealed would pass too; measured and derived records, which would tell the two apart, are upcoming.
A fail shows
What changed after sealing, and where. A rewrite shows as a failing signature or a head that misses the anchor.
A fail does not show
Who, when, which value is right, or that the change was improper.
