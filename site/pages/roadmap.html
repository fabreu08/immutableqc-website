In no fixed order, and with no dates. Each item is labeled Upcoming until it works.

2.1Agentic workflows Upcoming

Verified experiment data that AI agents could check before they use it in research and work, with the four checks shown on Check a record.

Check a record shows one record the way an agent would receive it, as JSON. It is a preview, not an API. It would need a documented record schema, keys published outside the lab and a shared registry first.

2.2Privacy on public networks Upcoming

Anything written to a public network should reveal nothing about results. A plain SHA-256 of a few guessable fields can in principle be matched by trying likely values, so a plain fingerprint is not enough. When anchoring becomes available it will write only a batch fingerprint, never the values; even so, two anchors one record apart would let the record between them be tried the same way.

  • FirstSalted (hiding) commitments in place of plain fingerprints. The lab keeps a random salt, and what is published reveals nothing without it.
  • LaterZero-knowledge proofs, so that a lab can show a property, such as “within specification” or “reviewed before release”, without disclosing the value.

2.3Anchoring on a public test network Upcoming

Anchoring will write a batch fingerprint, with a time, to a registry on a public test network, so that a later rewrite of the record history shows against a fingerprint the lab does not control. The registry code (a smart contract) is written; nothing on this site or in the console writes to a network, and every anchor shown here is simulated. A test network can be reset, so this is a first step; anchoring on Filecoin itself (2.4) will follow.

IQC-HS-01 §7Anchoring a batch

2.4Filecoin integration Upcoming

Anchoring batch fingerprints on Filecoin itself will follow the public test network. The details are not decided.

2.5Per-analyst signatures Upcoming

Each analyst would sign with their own key, in place of the one server key. Electronic signatures under 21 CFR Part 11 need more than a key: verified identity, the signature’s meaning, and controls over credentials.

2.6Signatures that cover each record’s position Upcoming

Today each signature covers only its own record’s fingerprint, as in the alpha app. So a record removed or moved, with every later link rewritten, passes every check except an anchor taken earlier. Signing the record’s link, which depends on its position and on every record before it, would show that change without an anchor. It would change the alpha app and these pages together.

2.7Reviewer sign-off Upcoming

Second-person review recorded as a signed record that names the records it covers, signed with the reviewer’s own key.

2.8Server-side verification in the app Upcoming

The alpha app recomputing every fingerprint, link and signature on the server, as these pages and the console do in your browser.

2.9Sample and method metadata in the seal Upcoming

Sample, method, injection and retention time sealed inside each record, not shown beside it; and a correction’s reason and reference sealed with it.

2.10A shared registry Upcoming

One public registry of batch fingerprints, which anyone would be able to check; no lab would have to run its own.

3Not claimed

Nothing is in production use. There are no customers, no electronic signatures, no validation, no instrument capture and no Filecoin storage, and nothing on this site writes to a public network.
