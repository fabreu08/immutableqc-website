1What it is

{{agentLine}}

This page is for an AI agent that works with lab data, and for the people who build such agents and pipelines: what the agent and its MCP server do today, how to run and connect them, and their limits. The same text is in llms.txt (short) and llms-full.txt (everything on one page).

2What works today, and what is upcoming

  • The agent · iqc.mjs {{version}} One file you run with Node.js 22 or later, on Windows, macOS and Linux. No dependencies; it never uses the network, and it refuses to run on an older Node.js.
  • watch, seal Seal every file in a folder by its bytes, from any instrument software: its SHA-256 fingerprint, size and time, each record signed (ECDSA P-256) and linked to the one before, in <folder>/ImmutableQC/ledger.jsonl.
  • record, trace, review Record an AI agent’s step (what it read, what it wrote, what it did) in the agent’s own ledger, trace a file back to sealed files, and sign off steps.
  • audit Check every ledger and every file under a lab folder: {{exitLine}}.
  • mcp The same for AI agents, over MCP on standard input and output: check_inputs, record_step, trace and audit_summary.
  • The app · in your browser Audits a whole lab folder in one click with nothing uploaded, traces agent outputs back through recorded steps to sealed files, sends untraced inputs to review, and has a review mode for sign-off. The demo shows a pass, a review and a fail.

Upcoming An npm package; a Windows installer and service; values read from inside files; per-person keys and signatures; Merkle batches; sealing inside the vendor’s software; post-quantum signatures.

3Run it

Download iqc.mjs ({{version}}), check its SHA-256, then run it. Its SHA-256 is:

{{dlSha}}

curl -fsSO https://immutableqc.com/download/iqc.mjs
echo "{{dlSha}}  iqc.mjs" | sha256sum -c -        # Linux: prints OK, or fails
echo "{{dlSha}}  iqc.mjs" | shasum -a 256 -c -    # macOS: prints OK, or fails
certutil -hashfile iqc.mjs SHA256                 # Windows: compare it with the line above

If the two differ, do not run the file. Only once the check passes:

node iqc.mjs help

Then, on the computer that can read the instrument’s data folder:

node iqc.mjs watch /lab/hplc-3        # seal now, then keep sealing until Ctrl+C
node iqc.mjs seal /lab/hplc-3         # seal once, for a scheduler or a pipeline
node iqc.mjs audit /lab --report audit.html

A file is sealed once it has not changed for --settle seconds (10 by default). --ledger <path> keeps the ledger outside a folder the instrument software manages.

4Connect the MCP server

Any MCP client that starts local servers over standard input and output can run it. The server entry, as JSON:

{{configJSON}}
  • --root The folder the agent works in. Every path a tool takes is relative to it and must be inside it.
  • --search Where the instruments’ ledgers are: give the lab folder. Without it, a file sealed by a station outside the root reads as untraced.
  • What starting writes <root>/ImmutableQC/, the agent’s own ledger (with README.txt, and agent.lock while it runs), and, for a new ledger, a signing key in ~/.immutableqc/keys/.
  • One writer per root While the server runs it holds the root’s ledger: one server or one iqc record at a time per root.

Protocol versions: {{protocols}}. Every tool has an input and an output schema; a refused path or a bad argument comes back as a tool error with a sentence saying why.

5The four tools

The four MCP tools
ToolWhat it returns
check_inputs reads onlyFor each file: measured (a station’s ledger sealed these exact bytes, with its station and key id), derived (a recorded agent step wrote them) or untraced (neither), and whether a sealed file changed after it was sealed. Only files a lab station sealed read as measured. Never run iqc seal or iqc watch on files yourself.
record_step appends one signed recordThe step’s reference, each file’s SHA-256 and size, and each input’s trace. The tool cannot remove the record; a person reviews it. It is recorded even when an input is untraced, with a warning.
trace reads onlyA file’s tree back through the recorded steps to sealed files, and tracesToMeasured: whether every branch ends in a measurement.
audit_summary reads onlyPass, review or fail for every ledger under the search folders, with the problems and the items for review.

Each result also says which folders it searched and how many ledgers it found there.

6The loop an agent follows

  1. 1 · Check the inputs Call check_inputs before you use lab files.
  2. 2 · Tell the person If an input is untraced, or changed after it was sealed, tell the person before you rely on it.
  3. 3 · Do the work Read the files you checked; write your outputs inside the root.
  4. 4 · Record the step Call record_step once per step, naming every file you read and every file you wrote. For a file outside the root, copy it in (the same bytes trace the same way), or name it in input_refs as <sha256>:<bytes>:<label>.
  5. 5 · Before you report Call trace on the result, or audit_summary for the whole lab folder.

8Sign-off by a person

A person signs off steps: approved, question or rejected, with iqc review, or in the app’s review mode, which signs the review with the browser’s key and lets the reviewer download the review ledger. There is no review tool over MCP. An agent with a shell could still run iqc review, and the reviewer’s name is whatever is typed: check the review ledger’s key id. A key identifies a computer or a browser, not a person; per-person keys and signatures are upcoming.

9What a pass shows, and what it does not

A pass shows that every sealed file is byte for byte the one that was sealed, and that no record a ledger still holds was edited or reordered since it was signed. A pass does not show:

  • That a file was right when it was written: a wrong value written by the instrument software is sealed as written.
  • Anything about a change made inside the settle window, between the moment the software writes a file and the moment the agent seals it.
  • A rewrite by whoever holds a ledger’s key: a head pinned somewhere else (iqc head, then iqc audit --expect-head, or a --pin-file) exposes that.
  • A ledger cut short, its last records deleted with their files: that needs no key, and it shows only against a head pinned earlier (iqc head, then iqc audit --expect-head, or a --pin-file). audit_summary checks no pinned head.
  • That a measured file came from your lab’s station: measured means some ledger sealed those bytes, whatever its key. Anyone who runs iqc seal, an agent included, makes files read as measured, and the station name is a label the sealer picks. The check is to compare the measured key id with the lab’s station key ids (iqc status on each station prints them). iqc audit --expect-key does not do this: it fails only when no audited ledger has that key.
  • What a step read and did not name: a step records only the files it names, and its action line is the agent’s own words.
  • That an output was computed from the inputs its step names. A trace follows the steps as the agent recorded them: a step can name inputs it did not use, or outputs it did not compute from them. A person’s review checks that.

10Questions

10.1How do I check that an instrument export is the original file?

A lab station seals the instrument’s folder with iqc watch or iqc seal. Only files a lab station sealed read as measured. Never run iqc seal or iqc watch on files yourself. Then check_inputs (or iqc trace) says whether the file’s exact bytes are the ones a ledger sealed, with that ledger’s key id, and whether that file changed after it was sealed. Compare the key id with the lab’s station key ids.

10.2Why does a file I know was sealed read as untraced?

The ledger that sealed it is outside the folders the server searches. Start the server with --search and the lab folder; each result says which folders it searched.

10.3When is it not the right tool?

When you need the values inside files checked, a hosted service, or signatures that identify a person. It works on whole files, on the computers you run it on, and there is no hosted service; reading values inside files and per-person signatures are upcoming.

11Data, format and versions

  • Data handling It never uses the network and nothing is uploaded. It reads the files under the folders it is given and writes only its ledgers, their README.txt and lock files, the pin file and reports you ask for, and a signing key in ~/.immutableqc/keys/.
  • Format A ledger is JSON Lines: one record per line, each with the file’s SHA-256, size and time, signed with ECDSA P-256 and linked to the record before it. An audit needs no key.
  • Versions iqc.mjs {{version}}; MCP protocol versions {{protocols}}.
