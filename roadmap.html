Roadmap

1Today: open alpha

  • These pagesOne synthetic HPLC sequence, signed with a demo key at build, with a simulated anchor. Your browser recomputes every check.
  • Agent · iqc.mjsSeals every file in a folder by its bytes, from any instrument software, in a signed ledger inside the folder; records the steps AI agents take on files (what each step read and wrote, by SHA-256); traces a file back to sealed files; and serves the same to AI agents over MCP. One file for Node.js 22; it never uses the network.
  • App · in your browserDrop a lab folder to check every file against the ledgers in it; nothing is uploaded. Agent steps show traced back to sealed measurements, and untraced inputs go to review. It can also seal a folder, and a demo shows a pass, a review and a fail.
  • Reviewer sign-offA person signs off agent steps (approved, question or rejected) with iqc review or in the app’s review mode: a review record names the records it covers. Its key identifies a computer or a browser, not a person; per-analyst signatures (2.5) are upcoming.
  • Alpha app · not publicImports HPLC CSV files and seals each peak area with one server key, by the same rules.

IQC-AG-01For AI agents: the agent and its MCP server

2Upcoming

The automated-lab items first, then the rest; no dates. Each item is labeled Upcoming until it works.

2.1Sealing at capture Upcoming

The orchestrator or driver would fingerprint, link and sign each result as it is produced, before anything downstream could change it. Adapters would speak SiLA 2 and OPC UA LADS; the first adapter would seal the results of one SiLA 2 device, with the sample, the well or position and the method inside the seal (2.8). Anything before capture would still not be covered.

2.2Measured and derived records Upcoming

A fingerprint shows that a record has not changed since it was sealed, not that it was ever measured. Only a record sealed at capture, by the instrument’s or orchestrator’s key, would count as measured; anything an agent, a script or an analysis produces would be a derived record, under a different signer, citing its sources. So a number either traces back to a measurement or it does not. Today the agent does this for whole files, from the steps agents record and with any ledger’s key (section 1): a file some ledger sealed counts as measured, and a file a recorded agent step wrote counts as derived. A trace follows the steps as the agent recorded them: a step can name inputs it did not use, or outputs it did not compute from them. A person’s review checks that. Sealing at capture under a key agents cannot use would expose an invented or hallucinated value with no measurement under it, which hashing alone cannot catch. A derived number that cites real measurements but was computed or copied wrongly would still pass, so a checker would re-run the analysis from its cited inputs. This would hold only if agents and scripts cannot use the capture key, which would seal the device’s identity with each result.

2.3Lineage and recall Upcoming

Derived records would form a lineage graph: measurement, analysis, model, decision. A corrected measurement’s reach would be computable in one step: every analysis, model and decision recorded as a derived record that cites it, and which agents must re-check. It would be a data recall, like the impact assessment of an out-of-specification investigation; work recorded any other way would stay invisible to it.

2.4Merkle batches with salted leaves Upcoming

One 32-byte root would commit to a whole run. A short path of hashes, an inclusion check, would show that one record is in the batch without revealing the others’ contents (it would show how many records the batch holds, and this one’s place), for selective disclosure when a lab chooses to hand one record to someone, by its own means. Every leaf would be salted with a random value the lab keeps. Each root would also commit to the root before it, so a dropped batch or a restored backup would break the sequence, checked against a root the lab pinned earlier outside its system. The construction would be the tree hash of RFC 6962, kept in RFC 9162, with domain separation and no duplicated leaf, as Certificate Transparency logs and Rekor use it.

2.5Per-analyst signatures Upcoming

Each analyst would sign with their own key, and reviewer sign-off (section 1) would then name a person, not a computer or a browser. An electronic signature under 21 CFR Part 11 needs more: verified identity, meaning and controlled credentials.

2.6Signatures that cover each record’s position Upcoming

Today a record removed, moved or copied to a second position, with every later link rewritten, passes every check but an earlier anchor, and that needs no key. Signing each record’s link would show it to anyone without the signing key; a rewrite by whoever holds it, or records dropped from the end, would still show only against an anchor.

2.7Server-side verification in the app Upcoming

The alpha app recomputing every check on its server.

2.8Sample and method metadata in the seal Upcoming

Sample, method, injection and retention time sealed inside each record, with a correction’s reason and reference.

2.9Post-quantum signatures Upcoming

Long term. SHA-256 and Merkle trees would hold up against a quantum computer; the ECDSA P-256 signatures would not. First would come algorithm agility, an algorithm id on every signature. Then would come hybrid signatures with ML-DSA (NIST FIPS 204) or SLH-DSA (FIPS 205), and old records would be re-sealed under the stronger algorithm, covering each record’s signature as well as its fingerprint (RFC 4998).

3Not claimed

Nothing is in production use: no customers, no electronic signatures, no validation, no capture at the instrument or orchestrator and no post-quantum signatures, and nothing on this site or in the app writes to a network.
